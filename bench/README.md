# Banc comparatif côté à côte

Depuis un checkout Linux de LM Resizer :

```bash
./bench/rejouer.sh
./bench/test-clean-tree.sh
```

Le script installe RTK 0.50.0 (archive vérifiée par SHA-256) et Headroom 0.39.1 avec ONNX Runtime 1.24.4 uniquement sous `target/banc/`, puis compile et lance le harnais Rust. Rapport, sorties brutes, `resultats.json` et `preuve_home.json` générés restent sous `target/banc/` ; le rejeu ordinaire ne modifie aucun fichier suivi. `test-clean-tree.sh` exécute le banc entier et vérifie cet invariant. Pour publier explicitement une nouvelle mesure dans les fichiers versionnés de `bench/`, utiliser `./bench/rejouer.sh --update-repo`. Un chemin de rapport dans le checkout hors `target/banc/` est refusé sans cette option. `target/` est ignoré par git et exclu du test `repository_has_no_python_runtime_surface`. Aucun fichier Python n'est versionné ; la fixture de code Python est conservée comme texte et copiée sous `target/banc/fixtures/` avec son extension naturelle au moment du rejeu. L'adaptateur Headroom dans `headroom_once.sh` utilise l'API publique par l'interpréteur isolé, sans script Python dans le dépôt.

`LM_RESIZER_BIN=/chemin/vers/lm-resizer` sélectionne un binaire d'une autre révision. Pour mesurer le code d'une autre révision, exécuter le banc depuis son checkout. Le corpus et ses oracles sont versionnés dans `cases.json` et `corpus/`. Les 23 cas couvrent tests, git, Docker, PostgreSQL, journaux, JSON, erreurs de compilation, six langages et prose. Trois sorties (`compile_error`, `git_diff`, `dotnet_ok`) ont été capturées en lançant les outils réels ; leurs sources et commandes sont dans `capture-src/README.md`. Les autres fixtures sont synthétiques. Aucune ne contient de donnée personnelle.

Le harnais compare les mêmes octets avec `o200k_base` de `tiktoken-rs`. LM Resizer utilise `exec` ou `compress --input`, RTK les filtres ou commandes décrits par cas, et Headroom `compress(messages)`. Les commandes sont simulées par des exécutables qui rejouent la fixture et son code de sortie. Le chemin du checkout et HOME sont normalisés dans les sorties comptées ; les sorties brutes et leurs empreintes restent sous `target/banc/results/`. La latence inclut le lancement de chaque processus. Une économie avec oracle incomplet vaut zéro ; un gain nul n'a pas de gagnant. Les détails des 69 mesures sont dans `resultats.json`.

Le format JSON compact de LM Resizer utilise `columns` et des `rows` positionnelles : chaque objet d'origine est reconstituable en associant les colonnes aux valeurs. L'original est aussi conservé dans CCR. Les sorties de `exec` portant un marqueur `[raw: <préfixe>]` se récupèrent avec `lm-resizer tee read <préfixe>` dans le même répertoire d'état ; le banc conserve en plus les sorties de chaque outil sous `target/banc/results/`.

Le cas Git exige les 46 sujets et un SHA abrégé qui identifie uniquement le commit visé parmi ceux de la fixture. L'oracle JSON vérifie le compte de 180 lignes, l'anomalie et trois lignes témoins ; il ne vérifie pas chaque valeur des 180 lignes. Le format tabulaire compact vient de `compact_json_rows`. Une reconstruction indépendante de toutes les lignes est nécessaire pour affirmer une égalité intégrale. Les tests Rust du harnais protègent les faits déclarés par les oracles et la validité des hunks Git capturés. La tâche agent reste non évaluée : l'essai antérieur a échoué sur un verrou de sandbox avant toute modification et ne figure pas au classement.

Les oracles `npm_ok` et `pytest_ok` acceptent des formulations équivalentes des comptes de réussite. Ils exigent aussi la portée exécutée (nombre de fichiers pour npm, chemin de test pour pytest) : `PASS (60) FAIL (0)` et `Pytest: 70 passed` conservent le compte, mais ne disent pas quels fichiers ont été exécutés. Le cas `prose` mesure 35 occurrences d'une ligne identique, pas une prose littéraire variée. La fixture `logs` utilise un horodatage ISO suivi d'un niveau `INFO` ; elle ne représente pas le format court par défaut de `journalctl`.

`resultats-avant.json` conserve le premier rejeu sur `753e42c99c338487e1dea98de402cbfecc473cf2` avant les corrections de compression, avec l'ancien corpus. Les trois cas remplacés par des captures réelles ne sont donc pas directement comparables à leurs lignes « avant ». `resultats.json` et `RAPPORT.md` décrivent le rejeu final ; le rapport indique l'empreinte exacte du binaire compilé depuis son checkout. Le classement publie les cas perdus tels quels.

## Capture `git_log_stat` et jetons réellement comptés

`capture-src/git-log/capture.sh` crée 40 commits dans un dépôt temporaire, avec une identité fictive et des dates fixes, puis capture `git log -40 --stat`. Le corpus contient des sorties réelles de Git sur des fichiers générés. L’oracle comporte 480 faits associés aux hashes complets : auteurs, dates, titres, fichiers, totaux et histogrammes. Il exige une égalité du fait entier dans son commit et rejette les titres suffixés, histogrammes altérés, fichiers manquants et échanges de commits. Comme `git_diff`, le cas est rejoué par `exec` via un exécutable Git de substitution ; RTK utilise ici sa route native `git log -40 --stat`, Headroom son API publique, sur les mêmes octets.

Le rejeu versionné au commit d’implémentation `83e9b25` est en profil release et comprend 69 mesures sur 23 cas. `o200k_base` reste le compteur commun. La latence inclut maintenant le comptage BPE de chaque nouveau historique `exec` de LM Resizer ; elle n’est pas une mesure de facture ou de session complète. Le compteur CLI conserve les champs JSON en octets ÷ 4 comme champs dépréciés et ajoute `token_savings`, avec méthode, dénominateur et valeurs signées.
