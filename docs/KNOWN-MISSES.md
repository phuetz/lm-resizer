# Limites des vues natives

La migration des filtres est en cours. Les mesures antérieures ne décrivent pas cette version. Voir [le banc](../bench/native/README.md) pour les écarts mesurés, les commandes restantes et la récupération du brut.

## `git log` : ce qui reste brut

Depuis 0.2.6, la vue d'un `git log` ne fait plus disparaître de commit parce qu'elle ne s'applique qu'au **format par défaut**, et seulement quand rien ne peut l'avoir changé. La vue par commit (en-tête, `Merge:`, `Author:`, `Date:`, titre et trois lignes de corps au plus ; le reste est compté dans `[+N message lines omitted]`, les pieds `Signed-off-by` et `Co-authored-by` sont retirés ; `--stat` ajoute chaque fichier avec son nombre de lignes, sans les barres de proportion) n'est rendue que si la commande n'a ni `--format`, ni `--pretty`, ni `--oneline`, ni `-z`, ni option globale `-c` ou `--config-env`, **et** si `git config --get-regexp '^(format|log)\.'` ne trouve aucune clé (`format.pretty`, `log.date`, `log.decorate`…). La configuration est lue par git, avec les mêmes options globales (`-C`, `--git-dir`…), jamais déduite du texte de la sortie : un format qui imite un en-tête (`--format='commit %T%n…'`, où `%T` est un hash d'arbre) ne peut donc pas être pris pour du format par défaut. Dans tous les autres cas, et dans le doute (git absent, configuration illisible), la sortie est **brute**. Les options globales de git (`--no-pager`, `-C <dossier>`…) sont lues avant la sous-commande, donc `git --no-pager log` se comporte comme `git log`. Une sous-commande git sans vue native (`log`, `diff`, `show` et `status` en ont une), alias compris, est rendue brute. Une vue qui n'économiserait aucun jeton est remplacée par le brut. Le patch d'un `git log` n'est reconnu que si la commande le demande (`-p`, `-u`, `-U<n>`, `--patch…`, `--cc`, `-c`, `-L`, `--word-diff`) ou si la sortie a le format par défaut : un message qui commence par `diff --git` n'est pas un patch. Cette vue de patch ne tronque jamais et n'est gardée que si elle se déplie en l'original exact. Limite : la configuration est lue là où `lm-resizer` s'exécute (pour `tool-output` ou `pipe`, dans le dossier courant), pas là où le `git log` a été produit.

Limites : un titre ou une ligne de corps est coupé à 100 caractères, une ligne de métadonnées à 120 (le brut complet se relit par `lm-resizer tee read <identifiant>`). Conséquence mesurée le 8 octobre 2026 sur le banc de 61 captures : les cinq captures `git log` de plusieurs commits passent de 91 à 97 % de « réduction » (premier commit seul, comme l'oracle de comparaison, qui le fait toujours) à 0 à 38 %, la médiane de 30,43 à 21,32 % et la moyenne de 35,14 à 28,97 % (29,96 % après les corrections suivantes de la même préparation).
