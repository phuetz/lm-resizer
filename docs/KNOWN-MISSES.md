# Limites des vues natives

La migration des filtres est en cours. Les mesures antérieures ne décrivent pas cette version. Voir [le banc](../bench/native/README.md) pour les écarts mesurés, les commandes restantes et la récupération du brut.

## `git log` : ce qui reste brut

Depuis 0.2.6, `git log` n'est compressé que si le **format par défaut est prouvé**. C'est le cas seulement pour un appel direct de `git log` lancé par `exec` (ou `lm-resizer git log`) : ni `sh -c`, `&&`, `|` ou `;`, ni `--format`, `--pretty`, `--oneline`, `-z`, `--graph`, ni option globale `-c` ou `--config-env`, et `git config --get-regexp '^(format|log)\.'`, lu avec les mêmes options globales (`-C`, `--git-dir`…) dans le dossier de la commande, ne trouve aucune clé (`format.pretty`, `log.date`…). Alors la vue montre chaque commit (en-tête, `Merge:`, `Author:`, `Date:`, titre et trois lignes de corps au plus ; le reste est compté dans `[+N message lines omitted]`, les pieds `Signed-off-by` et `Co-authored-by` sont retirés ; `--stat` ajoute chaque fichier, sans les barres de proportion). Dans tous les autres cas la sortie est **brute** : `pipe` et `tool-output` n'ont pas de ligne de commande fiable et ne reconnaissent jamais un `git log` par son contenu ; une sous-commande git sans vue native (alias compris) est rendue brute ; et **tout interpréteur de shell** (`sh`, `bash`, `zsh`, `dash`, `ksh`, `ash`, `fish`, `csh`, `tcsh`, `pwsh`, `powershell`, `cmd`) dont la ligne n'est pas réduite à une seule commande simple (script composé par `;`, `&&` ou `|`, fichier de script, citation invalide) est rendu brut, **sans jamais passer par le résumé générique** : ni le producteur ni le format de sa sortie ne sont établis. Une ligne `sh -c 'git log --oneline'` (une seule commande simple) est lue comme cette commande, qui n'est pas un appel direct : brute elle aussi. **Deuxième règle, indépendante du nom du programme** : au moment où le résumé générique s'appliquerait, toute commande dont l'`argv` contient le mot `git` puis, plus loin, le mot `log` est rendue brute — directement, derrière un wrapper (`env`, `timeout`, `nice`, `stdbuf`, `xargs`…), dans un script passé à un shell (`sh -c`, `bash -lc`) ou dans le code d'un autre langage (`awk 'BEGIN { system("git log") }'`, `python3 -c`). Les mots sont lus sans reconnaître le programme appelant ; cette règle existe parce que `--format=%s` n'a aucun hash que la garde de contenu puisse suivre. Elle ne s'applique pas aux commandes qui ont une vue dédiée (`grep 'git log'` garde sa vue de recherche). Les options globales de git (`--no-pager`, `-C <dossier>`) sont lues avant la sous-commande. Le patch demandé (`-p`, `-u`, `-U<n>`, `--patch…`, `--cc`, `-c`, `-L`, `--word-diff`) garde son codec, qui ne tronque jamais et n'est retenu que s'il se déplie en l'original exact. **Garde de contenu, dernier rempart sur toutes les voies, résumé générique compris** : une ligne qui commence par un mot de **4 à 40** chiffres hexadécimaux, seul ou suivi d'un sujet, avec ou sans préfixe de graphe (`*`, `|`, `/`, `\`), ou un en-tête `commit <hash>` (son titre est la première ligne indentée du message) est une identité de commit. Si le brut en contient et que la vue en perd une seule — un hash, ou un sujet non vide — la vue est refusée et le brut est rendu. La garde ne reconnaît le contenu que pour refuser une vue. **Faux positifs assumés** : un mot de 4 à 40 lettres a–f ou chiffres en début de ligne (`added 3 packages`, `dead`, `face`…) compte comme une identité ; si une vue le supprime, elle est refusée et le brut est rendu (moins de compression, jamais de perte). **Ce qui n'est pas couvert** : un historique sans aucun hash (`--format=%s`) produit par un programme dont l'`argv` ne contient pas `git` puis `log` — par exemple un script ou un exécutable lancé directement par son chemin (`./show-history`), une cible `make` — n'a ni nom reconnu ni hash à suivre : le résumé générique, qui ne garde que les lignes de diagnostic, peut alors supprimer des sujets. Les formes à hash (`--oneline`, `--format=%h`, graphe), même à quatre caractères, restent protégées par la garde. Limites : le résumé générique reste appliqué aux commandes inconnues qui ne sont ni des shells ni des commandes dont l'`argv` contient `git` puis `log` ; la configuration est lue là où `lm-resizer` s'exécute ; les lignes de corps sont coupées à 100 caractères dans la vue, le titre ne l'est jamais ; et la garde parcourt toute sortie qui contient des identités (mesuré sur 18 Mo et 100 000 commits : 3,6 s et 430 Mo en `exec`).

Conséquence mesurée sur le banc de 61 captures : les cinq captures `git log` de plusieurs commits, passées par `pipe`, passent de 91 à 97 % de « réduction » (premier commit seul, comme l'oracle de comparaison, qui le fait toujours) à 0 %. Médiane 30,43 → 4,87 % et moyenne 35,14 → 28,39 % par rapport à la préparation avant correction de `git log`.
