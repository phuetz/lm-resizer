# Limites des vues natives

La migration des filtres est en cours. Les mesures antérieures ne décrivent pas cette version. Voir [le banc](../bench/native/README.md) pour les écarts mesurés, les commandes restantes et la récupération du brut.

## `git log` : ce qui reste brut

Depuis 0.2.6, `git log` n'est compressé que si le **format par défaut est prouvé**. C'est le cas seulement pour un appel direct de `git log` lancé par `exec` (ou `lm-resizer git log`) : ni `sh -c`, `&&`, `|` ou `;`, ni `--format`, `--pretty`, `--oneline`, `-z`, `--graph`, ni option globale `-c` ou `--config-env`, et `git config --get-regexp '^(format|log)\.'`, lu avec les mêmes options globales (`-C`, `--git-dir`…) dans le dossier de la commande, ne trouve aucune clé (`format.pretty`, `log.date`…). Alors la vue montre chaque commit (en-tête, `Merge:`, `Author:`, `Date:`, titre et trois lignes de corps au plus ; le reste est compté dans `[+N message lines omitted]`, les pieds `Signed-off-by` et `Co-authored-by` sont retirés ; `--stat` ajoute chaque fichier, sans les barres de proportion). Dans tous les autres cas la sortie est **brute** : `pipe` et `tool-output` n'ont pas de ligne de commande fiable et ne reconnaissent jamais un `git log` par son contenu ; une sous-commande git sans vue native (alias compris) est rendue brute ; et **tout interpréteur de shell** (`sh`, `bash`, `zsh`, `dash`, `ksh`, `ash`, `fish`, `csh`, `tcsh`, `pwsh`, `powershell`, `cmd`) dont la ligne n'est pas réduite à une seule commande simple (script composé par `;`, `&&` ou `|`, fichier de script, citation invalide) est rendu brut, **sans jamais passer par le résumé générique** : ni le producteur ni le format de sa sortie ne sont établis. Une ligne `sh -c 'git log --oneline'` (une seule commande simple) est lue comme cette commande, qui n'est pas un appel direct : brute elle aussi. Les options globales de git (`--no-pager`, `-C <dossier>`) sont lues avant la sous-commande. Le patch demandé (`-p`, `-u`, `-U<n>`, `--patch…`, `--cc`, `-c`, `-L`, `--word-diff`) garde son codec, qui ne tronque jamais et n'est retenu que s'il se déplie en l'original exact. **Garde finale, sur toutes les voies** : si une vue perd un hash de commit ou un sujet non vide que le brut présente, le brut est rendu. Elle ne reconnaît que les en-têtes `commit <hash>` (avec leur titre) et les lignes commençant par un mot de 7 à 40 chiffres hexadécimaux (`<hash> <sujet>` ou hash seul, avec ou sans graphe `*`/`|`) ; elle ne reconnaît le contenu que pour refuser une vue. **Ce n'est pas une garantie générale** : un programme qui n'est ni git ni un interpréteur de shell (un exécutable ou un script lancé directement, `python -c`, `awk`…) et dont la sortie est un historique git passe par le résumé générique, qui ne garde que les lignes de diagnostic et supprime les autres ; la garde ne protège alors ni les hashes abrégés de moins de sept caractères (`--abbrev=4`) ni les formats sans hash (`--format=%s`). Limites : le résumé générique reste appliqué aux commandes inconnues qui ne sont pas des shells ; la configuration est lue là où `lm-resizer` s'exécute ; les lignes de corps sont coupées à 100 caractères dans la vue, le titre ne l'est jamais ; et la garde parcourt toute sortie qui contient des identités (mesuré sur 18 Mo et 100 000 commits : 3,6 s et 430 Mo en `exec`).

Conséquence mesurée sur le banc de 61 captures : les cinq captures `git log` de plusieurs commits, passées par `pipe`, passent de 91 à 97 % de « réduction » (premier commit seul, comme l'oracle de comparaison, qui le fait toujours) à 0 %. Médiane 30,43 → 4,87 % et moyenne 35,14 → 28,39 % par rapport à la préparation avant correction de `git log`.
